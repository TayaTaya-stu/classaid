# 講義文字起こし・参照順序（025）

## 適用

既存023・024適用後、025をSQL Editorで実行し、サーバーをビルド・再起動する。
025適用前に新サーバーを起動すると音声全文保存・根拠検索は失敗扱いになる。投稿・投影は継続し、根拠不明の返信は予備返信になる。
既存の024は再実行不要。過去の音声ファイル・全文は復元しない。

## 記録

`lecture_transcript_segments`は音声認識が実際に返した文章を保存する。録音ファイル・音声Base64は保存しない。
`transcript_original`が認識原文、`transcript_search`は空白を除き英字を小文字にした検索用テキスト。原文は書き換えない。
1レコードは1回の認識処理で、通常は約15秒の録音1区間、遅延・再送時は最大7区間をまとめたもの。
`received_at`はAPIの受信時刻、`saved_at`はDB保存時刻。正確な発話開始・終了時刻や発話者ではない。
`keyword_contexts`はキーワードの前後の抜粋と対応ページ。`offset_in_search_text`は検索用文字列の1始まりの位置。
`recognition_status=empty`は認識結果が空だったことを示す。無音だったことまでは保証しない。
処理失敗は可能な場合`event_logs`の`lecture_audio_processing_failed`で区別する。DB自体が停止した場合はその失敗ログも保存できない。
古い`lecture_contexts.timeline`は抜粋であり、全文として扱わない。

## 軽さ・保持

全文は確認用の別テーブルに区間ごとに追記し、毎投稿で全文を送らない。
返信では直近6件とキーワードが一致した最大4件、その前後のレコードを検索する。
最初のキーワードも全文アーカイブから検索でき、古いレコードを600件で削除しない。
録音方式・認識モデル順・15秒区切り・25秒の認識上限・返信の5秒上限は維持する。
新しいAI呼び出しを要点整理のために追加しない。保存と検索のDB処理は追加されるので、本番負荷での実測は別途必要。
全文に授業外の話や誤認識が含まれうる。今回の追加テーブルは管理者側だけが読める。
全文の自動削除期限は今回設定しない。保存期限・削除操作は運用として別に決める。

## 時間順と根拠

実際の投稿レコードの`created_at`を参照期限に使い、再試行・ジョブ処理時刻を期限にしない。
その時点までにDBへ保存された音声記録だけを参照する。発話が先でも保存が遅れた区間は使えない、保守的な判定。
PDFは事前に用語索引を作るが、本文全体を生成モデルへ渡さない。
音声で登場を確認した語句とPDFページの対応だけを渡し、未習語が同じページにあっても背景説明として漏らさない。
出力中に未登場のPDF語句が現れた場合も予備返信に切り替える（人間自身が入力した語句の反復は除く）。
語句抽出・照合は文字列ベースで、意味全体の理解や認識の正しさを保証するものではない。誤認識・同義語・否定表現は実機で検証する。
`archiveCutoff`・`archiveRecordIds`・`referenceEvidence.recordIds`・`reachedPdfReferences`をAI返信ログに残す。
これらは渡した根拠の記録であって、AIが適切に使った証明ではない。研究評価では返信と根拠を人手で照合する。

## SQLによる確認例（読み取り専用）

```sql
SELECT id, received_at, saved_at, model_name, recognition_status,
       transcript_original, keywords, keyword_contexts
FROM public.lecture_transcript_segments
WHERE session_id = '今回の授業回UUID'::uuid
ORDER BY id;
```
