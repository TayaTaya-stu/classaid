# 150人分のローカル予備試験（2026-10-27）

## 結果と位置づけ
150クライアント相当で入室・投稿・閲覧・いいね・AI処理キュー・投影イベント取得を実行した。データ整合性は確認できた。同時に、直近100件のチャット履歴がAIだけになる問題を再現し、対応する人間投稿を一緒に取得/保持する修正で解消した。

これは実Vercel/Supabase/Geminiの150人性能試験ではない。PGliteは単一接続のSQLを直列化するため、本物のPostgreSQLの複数接続競合や接続プール上限の検証にもならない。ローカル測定時間を本番の速度見積もりとして使わない。

## 利用した実装と代替範囲
- 実際の入室API、投稿/閲覧API、いいねAPI、スクリーン投稿API、教授アプリが呼ぶlatest APIを、ループバックのNode HTTPサーバーから呼んだ。
- 参加者名正規化、HMAC入室Cookie発行/検証、ルーム権限照合、AIジョブサービス、投影イベント取得、現在のSQLマイグレーション全件を使用。
- Supabase Authのトークン照合は試験用IDマップ、PostgREST通信はPGliteへのアダプタ、Nextのリクエストコンテキスト/afterのホスト機能は試験用ラッパーに置き換えた。実際のNextサーバーそのものを起動したHTTP試験ではない。
- 外部AI生成関数を15msの固定応答に置き換えた。ジョブ処理・DB上の予算予約・生成結果保存は実装を使用したが、実際のプロンプト生成/音声参照・Google API・5秒の実待ち時間/クォータはこの試験では通していない。
- is_mock_ai=falseの授業設定でサービスを通し、代替生成結果のモデル名をlocal-stub-no-google、版をlocal-rehearsal-onlyとして区別した。
- 実Supabase、授業データ、実際のAPIキー、録音、教授アプリには一切接続していない。試験DBはメモリ内だけ。

## 見つかった表示問題と修正
修正前、返信がまとめて完成した条件で、直近100レコードがすべてAIになり、人間投稿0件・返信元なし100件を再現した。保存済みデータや投影APIのペアは維持されていたが、学生画面で人間の投稿のみを選ぶと空になる条件だった。

修正内容:
1. 投稿APIは100件の通常取得に加え、その中のAI返信に必要な人間投稿を同じ授業回・ルームから補う。最大200レコード。
2. クライアントは直近100件に対応する人間投稿を保持し、単純なslice(-100)で親を捨てない。全件更新と差分更新の両方に適用。
3. 親投稿を補った差分にはafterId以前のIDが含まれることがある。クライアントはIDで重複排除して保持し、最大IDを次の取得に使う。
4. いいね更新対象は表示上限に合わせて最大200件。ID文字列は4400文字以内、いいねスナップショットは通常取得と合計して最大400対象。
5. 親投稿のDB取得に失敗した場合は503。学生画面の既存データを消さない従来の通信失敗処理へ戻す。

修正後は同じ条件で人間100件・AI100件・返信元なし0件。遅れて届く返信の親の復元、重複排除、200件上限、人間のみ表示の元投稿保持、200件のいいね更新、親取得503を確認した。

新機能追加ではなく、既存の人間投稿とAI返信の組表示を、履歴上限でも維持する修正。ポーリング間隔、AIの文章、音声認識、授業時間、DB保存件数、同意処理は変更していない。
